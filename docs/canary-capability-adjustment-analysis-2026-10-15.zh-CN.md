# greeting 验收的能力要求分析与调整建议

日期：2026-10-15（Asia/Shanghai）。范围：分析能力要求是否过宽，输出建议。本轮仅执行只读查询和内存诊断，没有修改推导规则、成员配置或能力确认记录。

后续状态：本文件保留当时的只读分析。用户随后要求实际验收，适用性修复已实施且真实模型验证为 4/5 项，证据与当前确认清单见[修复及确认清单](canary-capability-revision-2026-10-15.zh-CN.md)。下文“尚未实施”描述的是原分析时点。

## 结论

对当前无依赖、无持久化、同步执行的 greeting 示例，原清单存在过度泛化。建议保留现有实现与测试成员，优先修正能力语义和推导依据，将实现成员要求从 6 项调整为 4 项，测试成员从 7 项调整为 5 项，共 9 个成员能力事实。

该建议尚未实施。即使调整为 9 项，现有成员仍缺少对应的可信 claim，不能据此宣称可分配或验收通过。此前 13 项清单没有获得用户确认，不应作为登记依据。

## 问题及影响

### 1. 字符串输入规范化触发通用数据变更资格

`src/workflow.ts:1066` 将 `data` 直接映射为 `data.change`；`src/workflow.ts:1128` 主要检查影响维度为 required、证据可解析以及路径相交，没有区分调用时字符串转换和持久化数据、共享状态、数据结构契约变更。

本例 Binding 的 data 原因是从姓名字符串生成规范化值，并明确没有持久化、聚合或存储责任。分析输入与输出数据是合理的影响分析；把这一事实直接升级成额外的数据变更资格，缺少清晰的能力边界。建议本例由 TypeScript、公开函数契约和异常处理能力覆盖，不额外要求 `data.change`。

### 2. 单元测试消费者触发集成资格

`src/workflow.ts:1067` 将 `consumer` 直接映射为 `integration.consumer`。本例 consumer 证据只有测试文件直接 import `greet`，没有 HTTP、RPC、MQ、适配器或其他需单独处理的运行时集成边界。

消费者应继续进入 Binding，确保测试导入与调用兼容。建议仅在存在有证据的集成边界时要求 `integration.consumer`，本例的直接导入由 TypeScript、函数契约和测试能力覆盖。

### 3. 验证任务继承实现能力，未完整区分验证职责

`src/workflow.ts:1138` 已避免仅凭验证关系自动要求 data 能力，但随后 `src/workflow.ts:1210` 对同 Binding 的依赖任务继承相关影响能力。本例 data 的证据本身也包括测试路径，与验证任务写入范围相交。因此只改前面的验证判断，不能消除本例的额外 data 要求。

验证成员可以只读实现文件并测试行为，无须承担实现任务的写入责任。建议继承依据为实际验证动作、访问权限和副作用；执行持久化 fixture、数据修复验证或集成交互时保留相应资格，普通函数输入输出断言则不继承无关的实现资格。

### 4. 能力定义缺少可审阅语义

实际七项定义的 description 均为 `Service-controlled Planning V3 capability <id>.`。`src/planning/assignment-stage.ts:37` 用同一模板自动生成定义，并允许全部职责，未提供能力覆盖范围、排除范围、证据标准或职责差异。

因此当前只能证明程序要求这些 ID，不能证明每个 ID 对应清晰的资格门槛。原确认清单中的中文解释是本例建议解释，不是已经发布的权威定义。建议先发布可审阅、版本化的能力定义，再登记具体成员资格，避免要求用户确认含义不明的标签。

## 可实施调整方案

1. **定义先行。** 为现有能力补充受控语义、明确排除项、确认需要的证据与角色边界。缩窄已有定义属于资格契约变更，必须发布新版本；旧 claim 不自动升级，旧 operation 的冻结证据保留。
2. **保留完整 Binding。** data 和 consumer 仍可为 required。新增结构化的变更/消费类型与能力推导证据，将“需要检查的影响面”和“执行者需要的专项资格”分开。不要使用姓名、项目名、目录名或中英文 reason 关键词识别本例来免除资格。
3. **确定性推导。** `deriveCapabilityRequirementDraftsV3` 从经过验证的语义类型、具体 ownership、任务动作与权限产生要求；结构化语义缺失时明确待澄清，不能默认免除。所有继承路径使用同一语义边界。
4. **按职责继承。** 对实现、验证、审阅分别确定必须执行的操作。验证普通输入输出不要求数据写入资格；创建持久化 fixture、验证事务/回滚/迁移或集成链路时保留实际能力要求。
5. **新运行重新审核。** 更新 derivationRuleVersion，保留原 13 项历史记录，创建新 operation 并重新完成 Plan Review、Assignment 和 TaskPreflight。若新运行确为建议的 4/5 项，再生成对应待确认清单，按正式入口登记人类确认事实。

该方案调整的是能力契约的准确性，原始行为、测试覆盖、权限、可信来源、独立验证及发布门禁保持完整。成员资格确认与最终计划审批分别保留真实记录。
