# Planning evaluation harness

Each directory under `cases/` freezes business invariants in `gold.json`. Gold V1 remains readable for historical fixture regression. New qualification cases use Gold V2 and additionally freeze `expectedReadiness`, normalized `expectedBlockingReasons`, `requiredEvidenceStages`, an optional paired case, and an independently reviewed self-digest. The grader now measures both false-ready and false-blocked outcomes, blocking-reason precision/recall, first-pass approvability, stage evidence, and the existing coverage, owner, task, assignment, abstention, and rewrite metrics. `allowedBindingOwnerPathsByRequirement` is a list of complete equivalent owner sets; one set must be covered, not every alternative at once.

Candidate V2 records `blockingReasons`, `reachedStage`, `completedStageEvidence`, and human review references. A legitimate early business block only needs records through its reached stage; a ready result must reach `preflight` and retain the complete planning contract. Reason facts compare `code + sorted subjectKeys`, not localized display text. Every metric report includes numerator, denominator, and applicability. A zero denominator is `not_applicable`, never an implicit 100%.

Run `pnpm eval:planning:subset` while developing the grader. This explicitly selects the original `large-typescript-owner` fixture and its five runs, so incomplete historical real batches do not prevent local fixture regression. For another local selection, run `node planning-evals/run.mjs --cases CASE_ID,CASE_ID`; omitting the selection still scans every case and fails on incomplete history. Selection never qualifies a release, and combining `--cases` with `--release` or `--manifest` is rejected. Run `pnpm eval:planning` for the release gate. The release command requires `planning-evals/release-manifest.json` by default; pass `--manifest /absolute/path/manifest.json` to select another frozen batch. The manifest explicitly lists every included case and Gold digest plus every attempt, including `model_failure`, `infrastructure_failure`, and `cancelled` attempts. Candidate attempts reference immutable JSON artifacts and bind their operation ID to candidate provenance. Failed attempts remain in the denominator instead of disappearing during retries.

Release qualification requires at least eight unique `repository.identity` values, 24 independently reviewed Gold V2 cases, ready and blocked cases with at least one paired recovery scenario, and five valid real-model candidates per case. Its versioned MetricPolicy must freeze thresholds for `falseBlockedRate` and `modelFailureRate`; a missing threshold is an incomplete gate. A case with many Requirement records is still one requirement sample, and copying one repository into several cases does not increase the repository count. Use `pnpm eval:planning:subset -- --output /absolute/path/result.json` to persist a machine-readable report. Frozen fixture outputs validate the grader contract but never qualify a release.

A `real_model` run must include provenance for a unique Planning operation. The provenance freezes the repository base commit and digest, source/team/Decision inputs, MetricPolicy, Prompt versions, model provider/id/version, sampling configuration, token/tool budgets, operation digest, and start/completion timestamps. Those frozen inputs, including the model configuration and budgets, must match `gold.json.releaseInput`. Merely changing `executionKind` on a fixture is rejected and repeated copies of one Planning operation do not count as five runs.

Release qualification also reads `canary/release.json` by default, or the path supplied with `--canary`. This report must match the package version and identify the immutable Planning operation, source snapshot, approved PlanSnapshot, Approval, ordered Dispatch chain, terminal TaskRuns, Delivery Integration, final Git commit, and converged review. Multiple started or partially-started Dispatches are expected for dependency DAG frontiers. Integration must still select exactly one completed TaskRun per approved Task; failed or cancelled attempts remain in the evidence chain instead of being hidden. Required Requirement/Acceptance coverage must be complete and both false-ready and false-converged must be false. Missing or malformed canary evidence fails the release gate; never add a synthetic report to make the gate pass.

Capture artifacts from a running loopback Harness without manually assembling JSON:

```bash
dsh-project-orchestrator capture-planning-eval PROJECT_ID OPERATION_ID CASE_ID RUN_ID --output planning-evals/cases/CASE_ID/runs/RUN_ID.json
dsh-project-orchestrator capture-release-canary PROJECT_ID --output planning-evals/canary/release.json
```

The service exports only terminal same-operation evidence and refuses missing provenance, stale digests, reused predecessor model lineage, false-ready assignments, uncovered required scope, incomplete Dispatch/TaskRun closure, or non-converged delivery. The CLI validates the versioned schema, writes through an `fsync`ed same-directory temporary file, and refuses to overwrite an existing artifact. Model catalog lookup failure does not stop Planning, but such an operation has no release provenance and cannot be exported as a real-model evaluation run.

Fresh candidate operations freeze evaluation inputs before the first requirements-model request. V2 export binds that durable record to the source, repository, team and capability facts, resolved Decision inputs, installed runtime digest, model route, and enforced budgets. The source fingerprint includes task language and parser version. Repository or assignment-input drift fails the operation. Stable input fingerprints exclude operation-specific identifiers while the operation digest preserves each run's identity. Complete capability definitions must be prepared before freezing Gold: automatic first-run catalog preparation is a real input change.

For an initial V3 project, `POST /projects/:projectId/capability-claims/prepare` with `capabilityIds` prepares only pending declarations from existing active members' declared capabilities. It never confirms a human capability fact. Use the separate confirmation API only with explicit authorization for the exact scoped claims. Once MetricPolicy and trusted team inputs are ready, `GET /projects/:projectId/planning-evaluation-input` previews the same release fingerprints before creating any candidate. It does not create a Planning operation or domain repository snapshot, rejects historical plan/resolved-Decision inputs, and rejects project/team/policy drift during preview.

`allowedBindingOwnerPathsByRequirement` covers complete future writable source/declaration and required regression paths from `Binding.allowedPathScopes`. Keep unchanged forwarding/export files in a separate inspection inventory; an inspection-only file is not automatically a mandatory writable owner. Freeze this distinction before reviewing Gold and running candidates.

Invocation constraints may be retained in non-product scope dispositions. Binding and Task prompts must receive those dispositions without reviving excluded product work. Evidence completeness does not authorize writes to unchanged consumers, documentation, manifests or CI; preserve the source's precise writable boundary and report a real conflict when required target work cannot fit it.

Review Gold's stage prerequisites as well as its final expectation. High-risk Scenario Coverage requires an actual independent project Reviewer before Binding. An assignment-abstention case can use a non-auto-assignable Reviewer with no execution claims, while preserving no eligible executor; a completely empty team can correctly block earlier. A pending material Decision stops before that later prerequisite. Missing prerequisite fixtures must be corrected as new frozen inputs, with the failed case, Gold and attempts retained.

Historical operations without a pre-model freeze remain V1 exports; they are never backfilled or accepted by a release manifest. V2 supports legitimate early business blocks with evidence only through the reached stage. Technical failures remain non-candidate manifest attempts and cannot be relabeled as correct abstentions.

The frozen Planning route and output limit also apply to named reviewers and assigned members doing TaskPreflight. Their Agent identity and persona remain intact; execution-time skill loading and tools are disabled during that frozen operation. Task execution outside Planning continues to use the member's configured route and tool policy. A per-request output limit is not a batch token or cost limit.

`scripts/run-planning-batch-budget-gate.mjs CONFIGURATION_JSON` provides a separate loopback HTTP gate for a bounded collection batch. It requires explicit model, upstream, token ceilings, ledger path and port, reserves the full model input/output ceiling durably before every completion request, and retains unknown or failed usage across restarts. It supports Chat Completions and Responses usage, including SSE. This is not active until the isolated Harness actually uses that listener without a direct fallback. Usage refunds assume the gateway enforces its declared context/output limits and reports usage truthfully; a violation halts the ledger. Never infer gateway prices from this token accounting.

A user may instead explicitly authorize an unlimited batch. Record `budgetMode: explicitly_unlimited` and `tokenLimit: null` in that batch's authorization, without claiming an aggregate hard ceiling or changing the model's per-request limits. This choice does not authorize capability attestations, task dispatch, publication, or omission of failed attempts.

For offline corpus review preparation, run `node scripts/prepare-release-corpus.mjs NEW_DRAFT_PATH` followed by `node scripts/prepare-release-input-review.mjs NEW_DRAFT_PATH NEW_REVIEW_DIRECTORY`. The second script verifies the fixed commits, clean checkouts, tracked owner/test paths and source hashes, then emits 24 standalone proposed PRDs, a review Markdown file and structured expectations. It refuses to reuse an existing destination. These are unsigned review inputs outside `cases/`, never a substitute for independently reviewed Gold, trusted scoped team facts, pre-model release inputs, a batch budget or real attempts. Proposed new tests are explicitly marked as absent current evidence.
